# fallback

## Rules
- Runs inside the metrics tree walk (`metrics::collect_units` calls `fallback::unit_sites` on every production unit node it already holds; units inside a Rust test region are not measured and Test files never rank): no second parse, no git, no graph. Nested units keep their own sites; closures and inline callbacks belong to the unit.
- A fallback site is, in Rust, a call of a `[fallback].methods_rust` method (`unwrap_or`, `unwrap_or_default`, `unwrap_or_else`, `or_default`) or `.ok()?` (a `try_expression` over an `.ok()` call); a bare `.ok()` anywhere else is not a site, so `x.parse().ok().unwrap_or(0)` is one site at the outer call and `a.unwrap_or(b.next().unwrap_or(""))` is two (the argument is a site of its own). In Python, `d.get(k, lit)` / `d.pop(k, lit)` / `d.setdefault(k, lit)` (a `python_default_getters` method call with two arguments, the second a literal), `getattr(o, k, lit)` (three arguments, the last a literal) and `x or lit` (a `boolean_operator` `or` whose right operand is a literal), never inside a `python_skip_or_in` unit (`__init__`, `__post_init__`: a constructor defaulting an optional argument). In TS, `a ?? lit` (`ts_operators`; `||` only with `ts_count_or`) and, only with `count_optional_chain`, every `?.` member / call / index (a default of `undefined`, never a parse default).
- A literal default is, in Rust, a literal token (integer, float, string, raw string, char, bool) also behind `&`, parentheses or a minus, `()`, an empty `[]`, `None`, an `empty_constructors` call with no arguments (`String::new()`, `Vec::new()`, `Default::default()`) or, for `unwrap_or_else`, the bare constructor path or a closure whose body is one; `unwrap_or_default` / `or_default` default to `Default::default()`. In Python: dictionary, list, tuple, set, `None`, string, integer, float, `True`, `False`. In TS: object, array, string, template string, number, `null`, `undefined`, `true`, `false`. A site whose default is not a literal (`s.strip_prefix("x").unwrap_or(s)`) stays a plain fallback.
- The receiver chain runs down from the site's receiver: the value of a field access, the function of a call, the operand of `?`, parentheses, `&`, `*` or `await`, the object of a member, attribute or subscript. Arguments are never entered. A site is a parse default iff the chain holds a call named in `parse_calls` (Rust: `parse`, `split`, `next`, `strip_prefix`, `from_utf8`, `splitn`, `split_once`, `trim_start_matches`), `parse_calls_python` (`split`, `rsplit`, `partition`, `rpartition`, `splitlines`, `readline`, `int`, `float`) or `parse_calls_ts` (`split`, `match`, `exec`, `parseInt`, `parseFloat`, `parse` for `JSON.parse`, `shift`, `pop`) AND its default is a literal. `self.x.unwrap_or(0)` has no call in its chain and is never a parse default, and `get` is no transform: `m.get(k).copied().unwrap_or(0)` defaults an absent key (the benign case the design excludes), while a `get` / `nth` on the output of a transform (`line.split(':').nth(1).unwrap_or("")`) is caught by the transform below it, since the walk runs the whole chain down. Rust macro bodies (`format!`, `println!`, `anyhow!`…) are token trees to the grammar and are not scanned, so a site inside one is missed.
- Per site: `line` (of the default call itself: the `unwrap_or` / `??` / `or` token, not the head of a chain broken over several lines), `kind` (`parse_default` / `fallback`), `default` (as written, cut to 40 characters; `?` for `.ok()?`, `?.` for an optional chain), `transform` (the chain's fallible call when one was found, whatever the kind) and `binding`, the name the value lands in: a `let` pattern (the element at the site's position when a tuple expression is bound to a tuple pattern; a `mut a` element is `a`), a declarator, an assignment target, a struct field initializer, an object key or a keyword argument; absent for a value returned or passed on.
- Per unit (`FunctionMetrics`): `parse_defaults`, `fallbacks` (every site) and `fallback_sites[]` (left out of JSON when empty). No per-file signal, no density, no percentile, no score weight, no section.
- The report gives every production unit with `parse_defaults >= min_sites` (2) whose bare name (owner stripped: `Repo.discover` is `discover`) matches none of `exempt_fn_patterns` its own reason: `parse swallows 5 parse failures with literal defaults (lines 157, 160, 161, 162, 163): a malformed line becomes header "", hash "", author "", ts 0 and subject ""`, listing every parse-default line once (`line 4` when there is one) and the distinct binding / default pairs in line order (a site with no binding contributes its default alone). Per file: most sites first, then line order, at most `max_reported_per_file` (3) lines, then `+N more function(s) swallow 2+ parse failures with literal defaults`. Never a sub-line of another reason, never a score input.
- `scry metrics` prints `155 fallback site(s), 6 parse default(s); 1 function(s) with 2+ parse defaults: src/paths.rs:39 Repo.discover (3)` under its header (the same gate and exemptions as the report); `--json` carries every unit's `fallback_sites[]`.
- An `exempt_fn_patterns` entry that is not a valid regex is ignored with a `warning: [fallback] …` line on stderr.
- Every knob lives under `[fallback]` in `scry.toml`: `methods_rust`, `parse_calls`, `empty_constructors`, `python_default_getters`, `parse_calls_python`, `python_skip_or_in`, `ts_operators` [??], `ts_count_or` false, `count_optional_chain` false, `parse_calls_ts`, `min_sites` 2, `exempt_fn_patterns` [^default, ^from_env, ^with_, ^parse_args, ^from_matches, ^configure, ^__init__$], `max_reported_per_file` 3.
